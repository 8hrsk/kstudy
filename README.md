# kstudy — Э1: метрики обучения без эталона

Стенд для проверки одного вопроса, от которого зависит всё остальное:

> Можно ли численно отличить заметку, в которой модель что-то поняла,
> от заметки, в которой она переписала слова, — не имея правильного ответа?

Ничего не обучается. Только замеры. Если метрика не коррелирует с человеческой
оценкой — вся программа стоит на песке, и лучше узнать это за неделю, чем за
полгода.

---

## Быстрый старт

**Windows 11 — см. [WINDOWS.md](WINDOWS.md).** Всё работает нативно, менять ОС
не нужно; но обычный `git clone` ядра там ломается, поэтому корпус забирается
скриптом.

```bash
# 0. окружение (машина с RTX 3060)
pip install torch --index-url https://download.pytorch.org/whl/cu124
pip install transformers numpy

# корпус: только нужные каталоги, несколько МБ вместо ~5 ГБ
python scripts/fetch_corpus.py --subsystem rcu --dest ./linux

# 1. инварианты метрики — без GPU, секунды
python tests/test_metrics.py

# 2. ГЛАВНАЯ ПРОВЕРКА — на настоящей модели, минуты
python scripts/smoke_gpu.py --model Qwen/Qwen3-1.7B

# 3. полный прогон Э1 — около часа на 40 чанков
python run_e1.py --kernel ./linux --subsystem rcu --n-chunks 40

# 4. контроли без разметки
python -m kstudy.analyze data/metrics.jsonl

# 5. разметить сотню примеров (~час) и посчитать корреляцию
python -m kstudy.rate data/notes.jsonl data/chunks.jsonl
python -m kstudy.analyze data/metrics.jsonl --ratings data/ratings.jsonl
```

Шаг 2 — точка невозврата. Если он провалился, шаги 3–5 не имеют смысла.

## Что меряется

Три величины, всё остальное — производные.

```
L_base = -log₂ P(C)              насколько чанк удивителен сам по себе
L_info = -log₂ P(C | заметки)    насколько помогает уже накопленное
Δ      = L_base - L_info
```

**Триаж** — учебный план, который не стоит ничего (оба числа с одного прохода):

| L_info/ток | Δ/L_base | класс | что делать |
|---|---|---|---|
| низкая | — | `known` | пропустить, генерацию не тратить |
| высокая | высокая | `zpd` | зона ближайшего развития — учить сейчас |
| высокая | ≈ 0 | `too_far` | отложить, нужны предпосылки |

**Ценность заметки** — закрытый экзамен:

```
выигрыш = [ L(A|Q) − L(A|Q,N) ] − λ·L(N)
```

Вопросы составлены по чанку, отвечать надо без чанка. λ = 1 — честный MDL,
без свободных параметров: заметка платит за себя собственной длиной кода.

## Две находки стенда

Обе всплыли при прогоне тестов и обе изменили конструкцию. Записаны как тесты,
чтобы не потерялись.

### 1. MDL на поверхности текста поощряет копирование

Первая версия метрики спрашивала «дешевле ли передать заметку плюс чанк при
заметке, чем чанк напрямую». Для этой задачи дословная копия — почти
оптимальный код: платим `L(C)` за копию и ≈0 за чанк, итого выигрыш ≈ 0, что
лучше любого сжатия с потерями.

Замер на стенде:

| заметка | экономия | выигрыш |
|---|---|---|
| копия | 95.9 % | −27 бит |
| осмысленная сжатая | 39.0 % | −227 бит |

Плата за длину этого не чинит — проблема в том, что `L(C)` берёт деньги за
точную словесную форму, а понимание к словесной форме не сводится.

**Отсюда экзамен.** Польза заметки на ответах *насыщается* (больше, чем
`L(A|Q)`, не сэкономишь), а цена растёт с длиной. Копия, будучи втрое дороже,
не может быть втрое полезнее — и проигрывает.
Тест: `test_saturation_penalises_expensive_note`.

### 2. Дословные ответы в экзамене возвращают ту же проблему

Если ответы — куски источника, копия снова выигрывает, теперь за счёт
посимвольного совпадения. Значит генератор вопросов **обязан перефразировать**
ответы прочь от формулировок источника. `run_e1.py` считает `exam_leakage` и
выбрасывает чанк при утечке выше 25 %.
Тест: `test_verbatim_exam_answers_reward_memorisation`.

## Предусловие: разрыв в битах на токен

Вся конструкция держится на том, что модель считает гладкую осмысленную
заметку **существенно дешевле** плотного технического источника. Нет разрыва —
цена заметки не отличает сжатие от копирования, и метрика не различает ничего.

Игрушечная n-грамма даёт 12.3 против 11.0 бит на токен — разрыва нет, и на ней
`good` от `copy` не отделяются. Это ограничение стенда, а не формулы: сама
формула проверена арифметикой (`test_saturation_*`).

`scripts/smoke_gpu.py`, проверка A, меряет разрыв на вашей модели. Нужно ≥ 1.25×.
Провалилось — не чинить остальное. Варианты: модель побольше; модель, менее
знакомая с доменом; либо честный отрицательный результат для этого корпуса.

## Пороги решения

Заданы заранее, чтобы не подгонять после того, как увидели числа.

| Spearman ρ | AUC | решение |
|---|---|---|
| ≥ 0.5 | ≥ 0.75 | идти в Э2 |
| 0.3–0.5 | — | метрику чинить, в Э2 не идти |
| < 0.3 | — | гипотеза не подтвердилась |

Перед ручной разметкой стоит посмотреть на контроли — они бесплатны:
если модельные заметки не отделяются от воды и копий, размечать рано.

## Структура

```
kstudy/
  scoring.py    Scorer: HFScorer (transformers) | CacheNgramScorer (тесты, без GPU)
  metrics.py    L_base, Δ, триаж, MDL-выигрыш на экзамене
  corpus.py     нарезка подсистемы ядра по смысловым границам
  notes.py      генерация заметок и экзаменов, контроли, детектор утечки
  rate.py       CLI ручной разметки (порядок случайный, тип заметки скрыт)
  analyze.py    Spearman с бутстрэпом, AUC, разделение контролей
scripts/
  smoke_gpu.py  проверки на настоящей модели; A — предусловие
tests/
  test_metrics.py  19 инвариантов, гоняются без GPU за секунды
run_e1.py       весь этап одной командой
```

### Про CacheNgramScorer

Игрушечная LM из трёх компонент: n-грамма с backoff, кэш по контексту и
**суффиксное совпадение**. Третья принципиальна: без неё дословная копия
экономит ~20 % бит, тогда как настоящий трансформер экономит ~95 % за счёт
индукционных голов. Суффиксное совпадение — индукционная голова на минималках,
и без неё стенд не воспроизводит режим, ради проверки которого нужен.

Что стенд проверить **может**: порядок и знак экономии, отсев воды и
нерелевантного, арифметику насыщения, абляции.
Чего **не может**: знак выигрыша на реальных текстах — только `smoke_gpu.py`.

## Подсистемы

`corpus.py` знает пресеты: `rcu` (по умолчанию), `block`, `slub`, `workqueue`,
`memory-model`.

`rcu` выбран потому, что документация превосходна, предмет заведомо тонкий, а
рядом лежит LKMM с `herd7` — машинный верификатор утверждений о порядке памяти.
Он понадобится в Э4 как ветка A: тот же пайплайн с настоящим верификатором
против ветки B без него. Разница даст число — какую долю верификатора добирает
проверка без эталона.

## Известные упрощения

- Нарезка C наивная (скобки в нулевой колонке); макросы и `#ifdef` местами
  режутся неудачно. На документации работает надёжнее.
- `HFScorer` при переполнении контекста режет только контекст, никогда target —
  иначе биты между чанками несравнимы.
- Триаж в Э1 использует документацию как «уже прочитанное». В полном цикле
  туда пойдут накопленные заметки, но обучения на этом этапе ещё нет.
- Одна оценка на заметку, один разметчик. Для публикации понадобится второй и
  расчёт согласия.
